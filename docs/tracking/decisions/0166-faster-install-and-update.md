# 0166 — Windows 업데이트는 바뀐 부분만 받고, 설치본의 파일 수를 줄인다

## 맥락

2026-11-25 사용자가 설치와 업데이트가 오래 걸린다며 줄일 방법을 물었다. 이 PC의 0.13.3 설치본으로 재 보니 설치 파일은 235MB, 풀어 놓은 크기는 931MB, 파일은 5,981개였다. 업데이트는 매번 설치 파일 전체를 받았다(`disableDifferentialDownload = true`, "릴리스에는 설치 파일과 `latest.yml`만 있으면 된다"는 정책).

시간은 두 곳에서 든다.

- **받기.** 설치 파일 전체 235MB. 그런데 CI(결정 0056)는 릴리스마다 `.blockmap`을 이미 붙이고 있었고, NSIS 설치 파일은 설치할 때마다 자기 사본을 `%LOCALAPPDATA%\ieumoffice-updater\installer.exe`에 둔다. 바뀐 부분만 받을 준비는 되어 있었다.
- **풀기.** Windows에서는 크기보다 파일 수가 시간을 먹는다. 설치 파일이 파일을 하나씩 쓰고, 백신이 하나씩 열어 보고, 다음 업데이트 때 이전 판의 제거 프로그램이 하나씩 지운다. 파일 수의 대부분은 두 묶음이었다. draw.io 묶음 2,901개(그중 도형 그림 `img/lib` 1,910개), 명령어가 쓰는 jsdom과 의존 패키지 1,954개(그중 `.d.ts`·`.map`·`.md` 등 실행에 쓰지 않는 파일 약 460개).

사용자는 "리스크 시험을 먼저 하고 권장안으로 작업하자"고 했다. 시험한 것:

- **바뀐 부분 받기.** 실제 릴리스로, 앱이 쓰는 electron-updater 6.8.9의 `GenericDifferentialDownloader`와 Electron 네트워크 실행기를 그대로 돌렸다. 0.13.2 설치 파일과 두 `.blockmap`으로 0.13.3 설치 파일을 조립하니 61.9MB(26%)를 54번의 요청으로 받았고 sha512가 `latest.yml`과 같았다. 0.13.0 → 0.13.3은 64.1MB(27%)였다. 이전 설치 파일이 없을 때, 이전 `.blockmap`이 없을 때(404), 이전 설치 파일이 손상됐을 때(sha512 불일치)는 모두 오류를 냈고, electron-updater는 이 오류에서 전체 받기로 넘어간다. 이 PC처럼 빠른 회선에서는 전체 받기(11초)와 바뀐 부분 받기(12초)의 시간이 비슷했다. 줄어드는 것은 받는 양이고, 느린 회선에서 시간이 준다.
- **jsdom 쪽 파일 빼기.** 설치본의 명령어 사본 두 벌 중 한 벌에서 실행에 쓰지 않는 파일을 지웠다(1,949개 → 1,488개). Markdown → 워드·HTML·HWPX, 워드 → Markdown·HTML, `docs read`·`docs apply` 결과가 두 벌에서 같았다.
- **draw.io를 asar 하나로.** 설치본의 draw.io 폴더를 asar 파일 하나(68MB)로 묶고, 편집기의 프로토콜 처리기와 같은 방식(`stat` → `createReadStream` → `Readable.toWeb`)으로 숨은 창에 띄웠다. 편집기가 떴고(폴더 2.0초, asar 1.6초), 2,888개 파일을 모두 프로토콜로 받아 원본과 바이트가 같은지 확인했다.

## 결정

- **Windows는 바뀐 부분만 받는다.** `apps/shell/src/main/updater.ts`에서 `disableDifferentialDownload`를 Windows에서만 끈다. 실패하면 electron-updater가 전체 받기로 넘어가고, 전체 받기는 지금처럼 이어 받기(`update-resume.ts`)를 거친다.
- **macOS와 Linux는 그대로 전체를 받는다.** Mac은 앱이 받은 zip을 스스로 설치하고(결정 0097) Linux AppImage도 다른 길이다. 둘 다 저장소 주인이 직접 확인할 수 없고, 바뀐 부분 받기를 시험하지 않았다.
- **`.blockmap`은 릴리스에 반드시 올린다.** CI의 Windows 빌드는 `.blockmap`이 없으면 실패한다. 손으로 올릴 때도 세 파일을 올린다(`docs/releasing.ko.md`). 빠뜨려도 업데이트가 깨지지는 않고 전체 받기가 된다.
- **draw.io 묶음은 asar 파일 하나로 싣는다.** `electron-builder.cjs`가 `modules/diagram`을 실을 때 `drawio/`를 빼고, `afterPack`이 electron-builder가 쓰는 `@electron/asar`로 `modules/diagram/drawio.asar`를 만든다. 편집기는 `drawioBundleDir`로 asar가 있으면 그것을, 없으면(개발 실행) 폴더를 읽는다. draw.io의 파일은 바이트 그대로이고(`apps/diagram/AGENTS.md`의 "draw.io의 파일은 고치지 않는다"), 담는 그릇만 바뀐다.
- **명령어의 jsdom 사본에서 실행에 쓰지 않는 파일을 뺀다.** `packages/cli/collect-deps.mjs`가 `.d.ts`·`.d.cts`·`.d.mts`·`.map`·`.tsbuildinfo`·`.md`·`.mdown`·`.markdown`·`.gitkeep`을 복사하지 않는다. 라이선스·고지 글(`LICENSE.md` 등)은 확장자와 상관없이 남긴다.

## 버린 대안

- **압축하지 않은 설치 파일.** 풀기는 빨라지지만 받는 양이 크게 는다.
- **jsdom까지 번들에 넣기.** jsdom은 자기 기본 스타일시트를 디스크에서 읽고(`style-rules.js`) 동기 XHR 작업 파일을 `require.resolve`로 찾는다. 번들러에서 고쳐 쓸 곳이 생기고, 명령어 단독 배포 묶음에도 닿는다. 파일 수 이득에 비해 위험이 크다.
- **jsdom 사본을 asar로 묶기.** 명령어는 `ELECTRON_RUN_AS_NODE`로 돌고 jsdom을 동적 `import()`로 읽는다. ESM 읽기가 asar 안에서 되는지 시험하지 않았다.
- **다른 편집기의 `modules/*`도 asar로.** 각 편집기의 파일 수는 10~220개로 작다. 이번에는 큰 묶음 둘만 다룬다.
- **Mac·Linux도 바뀐 부분 받기.** 위 "결정" 참고.

## 결과

- 파일 수, 설치 시간, 이 결정의 확인 결과는 아래 "확인" 절에 적는다.
- `apps/docs/src/main/updater.ts`(원본에서 온 단독 워드 앱의 업데이트 코드)는 셸이 쓰지 않으므로 그대로 둔다.
- 다음 릴리스부터 받는 양이 준다. 처음 이득을 보는 것은 이 변경이 든 판에서 그다음 판으로 올릴 때다. 이 변경이 든 판으로 올리는 업데이트는 아직 옛 설정이 돌고 있으므로 전체를 받는다.

## 확인

2026-11-26, 이 변경을 넣은 main(cafa9787d 위)으로 이 PC에서 `dist:win`까지 만들어 0.13.3 릴리스와 비교했다.

| 항목                                    | 0.13.3 릴리스 | 이 변경           |
| --------------------------------------- | ------------- | ----------------- |
| 설치되는 파일 수                        | 5,973         | 2,625             |
| 그중 draw.io                            | 2,888         | 1 (`drawio.asar`) |
| 그중 명령어(`cli/`)                     | 1,954         | 1,493             |
| 설치 파일 크기                          | 246.3MB       | 242.7MB           |
| 설치 파일 속 묶음 풀기(3회 평균)        | 49.1초        | 25.7초            |
| 풀어 놓은 폴더 지우기(3회 평균)         | 10.3초        | 3.0초             |
| 업데이트 때 받는 양(0.13.2 → 0.13.3 예) | 235MB         | 62MB(바뀐 부분만) |

- 풀기·지우기 시간은 설치 파일 안의 `app-64.7z`를 7-Zip으로 F 드라이브(USB SSD)에 풀고 `rmdir /s /q`로 지운 값이다. 설치 파일이 하는 일(파일 쓰기, 백신 검사, 업데이트 때 이전 판 지우기)의 대부분이고, 레지스트리 등록과 설치 파일 사본 복사는 들어 있지 않다. 디스크와 백신에 따라 절대값은 다르고, 줄어드는 비율을 본다.
- 묶은 판(`win-unpacked`)을 창 없이 띄워 Markdown·CSV·draw.io 파일을 PDF로 내보냈다. 묶음 안 그림(`img/lib`)과 AWS 도형이 든 다이어그램의 PNG는 0.13.3 설치본이 낸 것과 바이트까지 같았다.
- 설치 파일은 서명되지 않은 채(`NotSigned`)이고 `.blockmap`이 함께 나왔다. 설치 창 문구·레지스트리 등록은 바꾸지 않았다.
- 사람이 남은 확인: 이 변경이 든 판을 실제로 설치해 다이어그램 탭을 열고 도형 목록을 몇 개 펼쳐 보기, 그 다음 판으로의 업데이트에서 업데이트 기록(`update-log.txt`)에 "Download block maps"가 찍히고 받는 양이 주는지 보기.
