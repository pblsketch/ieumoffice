# 0124 — 한글 엔진의 일괄 처리가 문단 모양·스타일·개체 편집도 끝에서 한 번 배치하고, 워드 → 한글 변환은 본문을 한 구역에 쓴다

## 맥락

결정 0121의 워드 → 한글 내보내기는 rhwp의 편집 호출로 문단을 하나씩 쓴다. 쓰기 전체를 엔진의 일괄 처리(`beginBatch`와 `endBatch` 사이)로 감쌌는데도 긴 문서가 오래 걸렸다(136쪽 2,482문단 40~46초). 변환기는 본문을 100문단마다 구역으로 나눠 쓰고 끝에 하나로 합쳐 이만큼 줄였다.

원인을 엔진에서 쟀다(2026-11-10). 빈 문서에 문단을 쓰며 일괄 처리 안에서 호출 하나에 드는 시간을, 구역의 문단 수만 바꿔 견줬다(같은 호출 5번의 중앙값).

| 호출                                             | 200문단 구역 | 1,600문단 구역 |
| ------------------------------------------------ | -----------: | -------------: |
| 문단 모양 `applyParaFormat`                      |         49ms |          317ms |
| 스타일 `applyStyle`                              |         60ms |          338ms |
| 머리말 글자 모양 `applyCharFormatInHeaderFooter` |         68ms |          453ms |
| 칸 속성 `setCellProperties`                      |        8.6ms |           49ms |
| 각주 넣기 `insertFootnote`                       |        6.8ms |           84ms |
| 대조: 글자 모양 `applyCharFormat`                |        0.1ms |          0.4ms |

- 문단 모양·스타일·머리말과 꼬리말 서식 호출(`applyParaFormat`, `setParaShapeId`, `applyStyle`, `applyParaFormatInHf`, `applyCharFormatInHeaderFooter`)은 일괄 처리 안에서도 `rebuild_section`으로 끝난다. 구역의 문단을 모두 다시 조합하고(글자 모양 잡기) 쪽을 나눈다. 호출 한 번이 그 구역을 `endBatch`의 쪽 나누기 한 번보다 오래 다시 배치했다.
- 표·칸·그림 속성과 주석 넣기(`setCellProperties`, `setTableProperties`, `setPictureProperties`, `insertPictureInCell`, `setCellPicturePropertiesByPath`, `insertFootnote`, `insertEndnote`)는 쪽 나누기는 미루지만 구역의 문단을 모두 다시 조합했다.
- 글자 모양과 글자 넣기·문단 나누기는 이미 `endBatch`로 미룬다. 상위 rhwp는 이 계약을 시험으로 지킨다(`body_ime_format_batch.rs`, #4118).

그래서 문단마다 모양을 입히는 쓰기는 구역 크기의 제곱으로 느려졌다. npm `@rhwp/core` 0.9.0과 상위 `devel`(`509c4c987`, 2026-11-09)도 같은 코드다.

편집기(rhwp-studio)도 여러 문단의 문단 모양, 셀 블록 서식, 셀 속성 대화상자를 `runInBatch`로 감싸고 "재페이지네이션을 묶는다(#4118)"고 적었지만, 문단 모양에는 효과가 없었다. 앱의 모양 복사(`format-copy.mjs`)도 스타일 걸기와 셀 속성을 같은 방식으로 감싼다.

## 결정

**엔진 패치 0043으로, 일괄 처리 안의 위 호출들이 구역을 호출마다 다시 배치하지 않고 `endBatch`에서 한 번 배치하게 한다. 일괄 처리 밖은 바꾸지 않는다. 변환기는 본문을 한 구역에 쓰고, 구역을 나눠 쓰던 우회를 지운다.**

- **엔진(패치 0043, `0.9.0-ieum.25`).** 일괄 처리 안에서는 고친 문단만 다시 조합한다. 주석을 넣으면 번호가 밀린 뒤 주석 문단까지 다시 조합한다(조합 결과가 주석 번호를 든다). 구역의 측정과 쪽 나누기는 `endBatch`의 쪽 나누기 한 번에 넘긴다. 이때 구역의 문단을 모두 다시 재도록 표시해, 일괄 처리 밖의 `recompose_section`이 남기던 상태와 같게 한다. 각주 번호·모양 맞추기(`refresh_footnote_numbers`)도 일괄 처리 안에서는 바뀐 각주를 든 문단만 다시 조합한다. 새로 내보내는 호출은 없다.
- **일괄 처리 안에서 읽는 값.** 문서 내용(문단 수·길이, 문단 모양, 각주 글, 표 칸)은 호출 바로 뒤에 맞다. 쪽 수, 쪽 배치, 커서 자리는 `endBatch` 뒤에 맞다. 글자 모양과 글자 넣기에서 이미 그랬던 계약이 문단 모양에도 걸린다. 변환기, 편집기의 `runInBatch`, 앱의 모양 복사는 일괄 처리 안에서 문서 내용만 읽는다.
- **변환기.** 본문을 한 구역에 쓴다. 100문단마다 구역을 나누고 끝에 합치던 쓰기(`SECTION_CHUNK`, `writePlan`의 구역 크기 인자, `ParagraphCursor.moveTo`, `convert`의 `sectionChunk`)를 지웠다. 쓰기 전체를 일괄 처리로 감싸는 것은 그대로이고, 이제 이것이 지켜야 할 규칙이다(`packages/docx2hwp/AGENTS.md`).

## 택하지 않은 것

- **변환기에서 구역 나눠 쓰기를 그대로 둔다.** 패치를 얹은 엔진에서는 나눠 쓰는 편이 오히려 느리다. 같은 문서(204쪽)에 나눠 쓰면 69.5초, 한 구역에 쓰면 22.6초였고, 나눠 쓸 때는 구역 나누기·합치기가 51초를 썼다(부하가 있던 한 번의 측정이지만 차이가 세 배다). 나눠 쓴 결과에는 합친 자리마다 저장 줄이 빠진 문단이 남는다(아래 "결과").
- **고친 문단만 다시 재게 한다(글자 모양의 지금 방식).** 처음에 이렇게 했더니, 한컴이 저장한 시험 문서(`memo-source.hwp`)에서 문단 모양을 바꾼 뒤 한 쪽의 표 행 높이가 호출마다 배치한 결과와 1e-14px 단위로 달랐다. 뒤 문단의 저장 세로 위치가 옮겨져도 표가 옛 측정을 써서다. 저장 바이트는 같았지만, 배치 결과를 그대로 같게 하려고 구역 전체를 다시 재게 했다. 다시 재는 일은 `endBatch`에서 한 번이다.
- **각주 넣기는 그대로 둔다.** 변환기가 한 구역에 쓰면 각주마다 구역 전체를 다시 조합해, 각주가 많은 긴 문서에서 다시 제곱으로 느려진다(1,600문단 구역에서 한 번 78ms).
- **`endBatch`에서 구역 전체를 다시 조합한다.** 조합은 문단마다 따로라서, 바뀐 문단만 다시 조합하면 결과가 같다. 끝에서 전체를 다시 조합하면 그만큼 시간이 더 든다.
- **상위에 바로 PR을 낸다.** 상위 PR에는 `devel` 위로 옮기기와 전체 회귀 확인이 필요하다. 먼저 이슈로 원인과 측정, 제안을 낸다(초안을 저장소 주인이 올린다).

## 결과

- **속도.** 다시 만든 두 문서를 `.hwp`로 바꾼 시간이다. 변환 한 번에 새 프로세스 하나를 띄우고, 지금 변환기 + ieum.24(전)와 새 변환기 + 새 엔진(뒤)을 번갈아 5번씩 돌렸다. 중앙값과 범위다.

  | 문서                                                            | 전                  | 뒤               | 짝마다    |
  | --------------------------------------------------------------- | ------------------- | ---------------- | --------- |
  | 혼합 문서 204쪽 2,484문단(제목, 목록, 4×4 표 108개)             | 129.6초(96.1~154.6) | 10.6초(9.5~14.4) | 9~12.5배  |
  | 가정통신문 47벌 94쪽 844문단(머리말, 쪽 번호, 합친 칸 표, 그림) | 27.1초(24.2~33.0)   | 3.5초(3.4~4.4)   | 6.9~8.0배 |

  0121이 적은 136쪽 문서는 다시 만들 수 없어 이 두 문서로 쟀다. 지금 남은 시간의 대부분은 문단마다의 일(글자 모양 호출 약 7,100번, 칸 문단 쓰기, 끝의 쪽 나누기 한 번)이고 문서 길이에 비례한다.

- **호출 한 번의 시간.** 위 표의 호출이 모두 구역 크기와 상관없이 1ms 아래다(200문단 / 1,600문단 구역: `applyParaFormat` 0.32 / 0.28ms, `applyStyle` 0.83 / 0.14ms, `applyCharFormatInHeaderFooter` 0.06 / 0.08ms, `setCellProperties` 0.35 / 0.18ms, `insertFootnote` 0.20 / 0.39ms). 쪽 나누기는 `endBatch`가 한 번 한다(약 0.4초).
- **저장 결과.** 엔진 패치는 저장 바이트를 바꾸지 않는다.
  - 워드 → 한글 변환 31개 문서(패키지 시험 문서 2개, 워드 편집기 쪽 나눔 견본 27개, 위의 긴 문서 2개)를 지금 변환기로 쓰면 ieum.24와 ieum.25의 HWP·HWPX 바이트, 쪽 수, 쪽마다 그린 SVG, `.hwp` 저장 검사가 31/31 같다.
  - 앱의 한글 시험 문서 38개(한컴이 저장한 HWP·HWPX)에 같은 편집(문단 모양, 스타일, 문단 모양 되돌리기, 칸·표 속성, 그림 글자처럼 취급, 중간 문단의 각주·미주, 머리말·꼬리말 서식)을 넣으면, 두 엔진에서 일괄 처리한 결과와 호출마다 한 결과 넷이 모두 같다(38/38).
  - 엔진 시험(`batch_layout_deferral_tests` 셋)과 앱 시험(`apps/hwp/tests/engine-batch-layout.test.ts`)이 일괄 처리 결과와 호출마다의 결과가 쪽 정보·캐럿·SVG·HWP·HWPX까지 같은지 본다. 문단 모양·스타일과 머리말 서식 시험은 ieum.24에서 실패한다(일괄 처리 중 쪽 수 1 → 4, 1 → 3).
- **한 구역에 쓰면 바뀌는 것.** 본문 블록이 100개 넘는 문서만 바뀐다. 나눠 쓴 결과에는 합친 자리(100블록마다)의 문단에 저장 줄이 없었다. `.hwp`에서는 그 빈 문단의 줄 기록이, `.hwpx`에서는 표 문단의 줄 배열이 빠졌고, 그 뒤 표 문단의 저장 위치가 빠진 줄의 간격(600HU)만큼 위였다. 한 구역에 쓰면 모든 문단이 저장 줄을 가진다. 엔진으로 그린 204쪽 가운데 1쪽에서 제목 한 줄이 8px 아래로 바뀌었고 쪽 수는 같다. 블록이 100개 이하인 문서(위 29개)는 바이트가 같다. 한컴 한글 2024로 열면 나눠 쓴 판과 한 구역 판이 모두 열리고 쪽 수와 글자 수가 같다(혼합 문서 `.hwp`·`.hwpx` 216쪽 186,082자, 가정통신문 94쪽 28,223자). 한컴은 열 때 다시 나누므로, 엔진이 그린 204쪽과 쪽 수가 다른 것은 이 결정 전후가 같다.
- **남은 차이(이 결정과 별개).** 일괄 처리 안에서 붙여넣어 만든 표에 칸 글을 넣으면, 표의 저장 높이가 붙여넣은 틀의 높이에 머문다. 호출마다 쓰면 칸 글을 담은 높이가 된다(가정통신문 표 3846 대 3946HU). 패치 전후가 같다. `docs/tracking/findings.md`에 적었다.
- 시험: ieum.25에서 한글 편집기 시험 1,399개(건너뛴 것 6개), 한글 파일 읽기 21개, 터미널 명령어의 한글 시험 80개, 변환기 시험 60개, 워드 편집기의 내보내기 시험 13개가 통과한다. 패치를 얹은 엔진 가지(`ieum/v0.9.0-batch`)에서 상위 엔진 시험 12,999개가 모두 통과한다(`cargo nextest`, 건너뛴 것 45개는 상위가 정한 것). 한 번에 돌린 실행에서는 메모리가 모자라 26개가 시작하자마자 끝났는데, 스레드 넷으로 다시 돌리자 모두 통과했다. 시간 제한으로 돌지 못한 550개도 따로 돌려 통과했다.
- 상위 이슈 초안은 원인 위치, 재현 코드(npm 0.9.0), 측정, 제안을 담았다. 올리는 것은 저장소 주인이 정한다.
