# 0165 — PDF 도구 v2(용량·스캔·변환 고도화와 도구 창 UX 혁신)와 끌어다 놓기 입력 채널

## 맥락

결정 [0030](0030-pdf-tools-hub.md)으로 홈 카드와 별도 PDF 도구 창을 연 뒤, 기본 도구 18개(직접 처리)와 편집기 넘김 카드 5개를 제공해 왔다. 실제 사용에서는 세 가지 요구가 컸다.

1. **용량·스캔·변환 공백**: 용량 구성을 보고 목표 용량에 맞춰 줄이거나(회색조·웹 빠른 보기·메타데이터 제거 포함), 단면 스캐너 홀짝 교차 병합, 축소판 기반 페이지 구성(순서·회전·복제·삭제·빈 페이지 삽입·다중 PDF 조합), 스캔 PDF 오프라인 OCR, 오피스·한글·마크다운·HTML·마인드맵·EPUB → PDF 일괄 변환, PDF → PNG/JPG/ZIP 내보내기, PDF → Word/Excel/PPT/HWPX/Markdown/EPUB 직접 변환을 도구 창 안에서 바로 끝내고 싶다.
2. **작업 흐름의 마찰**: 파일 대화 상자로만 넣어야 해 파일을 끌어다 놓을 수 없고, 단일 PDF 도구를 여러 파일에 한꺼번에 돌리거나(일괄 처리) 방금 만든 결과를 다음 도구로 바로 넘길 수 없으며, 암호가 걸린 PDF는 반드시 "암호 풀기"로 먼저 사본을 만든 뒤 다시 불러와야 했다.
3. **기존 경계 유지**: 결정 0030의 "경로는 메인 프로세스에만 두고 렌더러가 임의 경로를 보내지 않는다", "AI를 쓰지 않는다", "원본을 덮어쓰지 않는다", "새 외부 의존성을 추가하지 않는다"는 원칙은 그대로 지켜야 한다. 또한 다른 작업에서 고치고 있는 PDF 분할(`split`) 로직과 화면은 건드리지 않는다.

## 결정

1. **도구 창을 24개 직접 도구 + 3개 편집기 넘김 카드로 확장한다.**
   - 기존 편집기 넘김 카드 중 "이미지 내보내기"(`pdfToImages`)와 "PDF 변환"(`convertFromPdf`)을 도구 창 직접 처리로 승격하고, 새 도구 4개("페이지 구성" `organize`, "홀짝 교차 병합" `interleave`, "스캔 PDF OCR" `ocr`, "문서를 PDF로 변환" `docsToPdf`)를 추가한다.
   - 기존 "용량 줄이기"(`compress`), "PDF 병합"(`merge`), "이미지로 PDF 만들기"(`imagesToPdf`)를 고도화한다(용량 분석·목표 크기 이진 탐색·무손실/qpdf 최적화·회색조·메타데이터 제거, PDF/이미지/문서 혼합 병합·파일별 범위·책갈피·용지 통일, WebP/BMP/GIF·방향·화질 최적화·개별 회전).
   - PDF 편집기 페이지 탭의 "PDF 도구" 메뉴(`PDF_TOOLS_HANDOFF`)를 14개 도구로 넓힌다. `split` 도구의 처리·화면·시험은 건드리지 않고 일괄 처리와 결과 이어쓰기 대상에서 제외한다.

2. **끌어다 놓기 입력 채널을 preload 전용 `webUtils.getPathForFile`로만 허용한다(결정 0030의 입력 경로 규칙 보완).**
   - 렌더러에서 비롯되는 파일 경로는 메인 프로세스의 열기 대화 상자(`showOpenDialogWithMemory`)와 preload의 `dropInputs(files, kind, accept)` 두 길로만 제한한다.
   - `dropInputs`는 브라우저의 실제 OS 드롭 이벤트에서 받은 `File` 객체만 preload 안에서 `webUtils.getPathForFile(file)`로 경로로 바꿔 `pdf-tools:drop-inputs` 채널로 넘기며, 렌더러 JavaScript가 임의의 문자열 경로를 전달하는 API는 열지 않는다.
   - 메인 내부에서 신뢰하는 출처 4개(편집기 리본 넘김 `openPdfToolsWithFile`, 결과 이어쓰기 `promoteResult`, 입력 이어쓰기 `promoteInput`, 혼합 병합 백그라운드 임시 PDF `mix-queue`)도 모두 동일한 `inputsFrom()` 검사(실재 파일 여부, `MAX_TOOL_INPUT_BYTES` 1 GB 상한, 매직 바이트·디코딩·확장자 검증)를 통과한 파일만 불투명 ID(`toPublicInput`)로 돌려주고, 경로는 메인 `Map`에만 보관한다.

3. **암호 PDF 도구 내 잠금 해제는 메모리 전용이며 항목 제거·도구 이탈·창 닫기·앱 종료 때 즉시 비운다.**
   - 일반 PDF 도구에 암호 걸린 PDF를 추가하면 거부하지 않고 잠긴 상태(`encrypted: true`)로 등록하고, 도구 패널 안에서 암호를 입력받아 `unlockInput`이 작업 프로세스의 qpdf로 복호화한 바이트를 메모리에만 보관한다. 암호는 로그·오류·디스크에 남기지 않으며, 항목을 목록에서 빼거나 도구를 나갈 때(`releaseInputs`), 창을 닫거나 앱을 종료할 때(`cleanupPdfToolsOnQuit`) 암호 메모리·복호화 캐시·혼합 병합 임시 PDF와 진행 중인 자식 프로세스를 즉시 정리한다.
   - 잠금 해제된 입력을 사용한 결과 파일에는 원래 암호가 다시 걸리지 않으므로, 결과 화면에 암호 없는 새 사본임을 분명히 안내한다.

4. **새 의존성 없이 기존 앱 구성 요소만 재사용한다.**
   - PDF → 이미지 내보내기(`pdfToImages`)는 `pdf-structure` 작업 프로세스의 청크 단위 `renderPages(pages: number[])`로 BGRA 비트맵을 소량씩 받아 메인에서 `nativeImage`로 PNG/JPG 인코딩하고, ZIP 저장은 셸에 이미 포함된 `jszip`(STORE 압축)으로 묶어 대용량 300 DPI 문서의 메모리 급증을 막는다.
   - "문서를 PDF로 변환"(`docsToPdf`)과 혼합 병합의 비-PDF 변환은 셸의 `--headless-export` 경로를 `execFile(..., { shell: false })` 자식 프로세스로 호출해 GUI 상태와 격리하고, 취소·창 닫기·앱 종료 시 활성 자식 프로세스와 임시 폴더(`<tmpdir>/ieumoffice-pdf-tools-mix`)를 정리한다. HTML·마크다운 내 외부 웹 그림 URL 처리 정책은 일반 편집기의 PDF 내보내기와 같다.
   - 일괄 처리(단일 PDF 도구, `split` 제외)는 출력 폴더 하나를 골라 실패 항목은 건너뛰고 끝까지 완료한 뒤 요약을 보여 주며, 목표 용량 미달 시 단건은 사용자 확인을 받고 일괄은 최소 결과 저장 후 요약에 표시한다.

## 택하지 않은 것

- **렌더러가 문자열 경로 배열을 직접 IPC로 보내게 한다.** 임의 파일 읽기 취약점이 생기므로 금지한다. preload가 `File` 객체에서만 `webUtils.getPathForFile`을 호출해 OS 드롭 이벤트로 제한한다.
- **미병합 PR이나 새 이미지·압축 네이티브 패키지를 추가한다.** 설치 파일 크기와 라이선스 부담 없이 앱에 이미 있는 `nativeImage`, `jszip`, `qpdf-wasm`, `pdfium.wasm`, `rhwp`, `--headless-export`로 전체 기능을 구현한다.
- **압축·이미지 내보내기를 전체 페이지 한 번의 IPC 메시지로 전송한다.** 100페이지 300 DPI 기준 약 3.5GB BGRA가 한 번에 오가 8GB PC에서 실패하므로 DPI별 청크 렌더링으로 제한한다.
- **일괄 처리나 결과 이어쓰기에 `split`을 포함한다.** 별도 작업 중인 PDF 분할 기능과의 충돌을 피하고 분할의 다중 출력 시맨틱을 단순하게 유지한다.

## 결과

- 24개 직접 도구와 3개 편집기 넘김 카드가 22개 언어 문구·도움말·편집기 리본과 일치하며, 모든 경로 검사와 배선 규칙은 `apps/shell/tests/pdf-tools-wiring.test.ts`가 자동으로 지킨다.
- 도구 창은 AI와 무관하게 이 PC 안에서만 동작하며(HTML/마크다운 원격 이미지 참조만 일반 PDF 내보내기와 동일, `PRIVACY.md` 반영), 창 닫기·앱 종료 시 자식 프로세스와 임시 파일·메모리 암호가 남지 않는다.
