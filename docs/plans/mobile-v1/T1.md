## 1. 시제품 결과 (XLS-T1~T5)

엑셀 1판은 위험 여섯을 먼저 시제품으로 확인했다. 판정은 된다 / 조건부 / 안 된다. 확인은 Windows 미리보기(390px)와 Android 에뮬레이터(Android 16, x86_64)에서 했고, 실기기 확인을 대신하지 않는다. 원자료는 `F:\ieum-scratch\mobile-v1-t1\proto\T{1..5}-results.md`(git 밖).

### 1.1 엔진의 모바일 빌드 (시제품 3) — 된다

- 엔진 크레이트(`apps/sheets/native/xlsx-engine`)를 한 줄도 고치지 않고 앱 안에서 함수 호출로 부른다. 엔진의 명령 분기는 실행 파일(`main.rs`)에만 있어서, `src-tauri/src/sheets/engine-lib/`가 라이브러리 공개 함수 위에 같은 분기를 같은 순서로 다시 짰다.
- PC 사이드카 실행 파일과 비교했다. 같은 요청 17줄(실제 IronCalc 패닉 하나 포함)을 넣으면 응답 글이 키 순서까지 같고, 저장 파일 바이트도 같다.
- **엔진은 따로 빌드한다(사용자 결정).** 처음처럼 앱 크레이트에 바로 넣으면 엔진의 `zip 9`이 flate2의 `zlib-rs` 기능을 켠다. 그러면 앱 전체의 압축 구현이 바뀌어 휴대폰 한글 저장의 압축 바이트가 달라졌다(HWP 5 스트림 42,923 B → 42,418 B). 지금은 엔진을 자기 작업 공간의 정적 라이브러리로 따로 빌드한다. 공개 심볼은 `ieum_sheets_engine_*`만 남기고 나머지는 숨긴 뒤 앱에 붙인다(`src/sheets/engine_build.rs`, `build.rs`의 `// T1 sheets` 블록이 부름).
  - 앱의 `Cargo.toml`·`Cargo.lock`과 기능 나무는 T1 전(12923b5e6)과 같다.
  - 한글 압축 결과가 T1 전과 같은지 시험이 지킨다(`hwp_and_hwpx_compression_matches_the_app_before_the_engine`).
- **엔진이 멈춰도 그 요청만 실패한다(사용자 결정).** 엔진 라이브러리는 자기 빌드에서 `panic = "unwind"`이고, C 경계에서 `catch_unwind`로 받아 `workbook_error`로 답한다. 앱 프로필의 `panic = "abort"`는 그대로다. 에뮬레이터에서 실제 IronCalc 패닉이 그 요청만 실패시키고 앱이 살아 있음을 확인했다.
- **임시 파일 자리(T6과의 약속)**: 작업 폴더는 앱 캐시의 `ieum-tmp/sheets/`, 엔진 세션 캐시는 `ieum-tmp/sheets/engine/`(Android `TMPDIR`)다. 앱이 시작할 때 비운다. 웹뷰 파일 명령은 작업 폴더 밖과 `engine/`을 가리킬 수 없다.
- **앱 크기**: arm64 release `.so`가 11,030,088 B → 19,433,448 B(+8.01 MiB, gzip 약 +3.1 MiB)로 커진다. 엔진이 자기 표준 라이브러리를 따로 지녀서, 바로 넣었을 때보다 +0.45 MiB 크다.
- **iOS**: 엔진 크레이트와 엔진 라이브러리는 `aarch64-apple-ios`로 컴파일된다(F 드라이브에 따로 깐 도구). 앱 크레이트는 Tauri의 `objc2-exception-helper`가 `xcrun`을 써서 이 PC에서 확인할 수 없다. Apple 쪽 묶기(`ld -r -exported_symbols_list`)는 한 번도 돌지 않았다. → 실기기·Mac에서 볼 것(4절).
- **라이선스**: 엔진 의존 110개 모두 `apps/mobile/src-tauri/deny.toml` 허용 목록 안(수동 대조, cargo-deny 없음).

### 1.3 메모리 (시제품 2) — 된다(Android 기준)

| 견본                    | 앱 프로세스                           | 웹뷰 렌더러       | JS 힙   |
| ----------------------- | ------------------------------------- | ----------------- | ------- |
| 2,000행 rich            | 158 → 최대 196 MB                     | 104 → 최대 319 MB | ≤ 55 MB |
| 100,000행 rich(23.6 MB) | 엔진 색인 중 최대 309 MB, 뒤에 225 MB | 최대 291 MB       | ≤ 48 MB |

- 화면에 올리는 범위는 파일 크기와 상관없이 약 220행 × 30열이다. 고정 상한은 새로 두지 않았다. 합계 봉우리 약 600 MB는 iPhone 한도(1.5~2 GB)의 절반쯤이다. iPhone 숫자는 Mac에서 볼 것.
- **열기 시간이 문제다.** 100,000행 파일을 고른 뒤 첫 화면까지 79~~98초가 걸렸다. 엔진이 여는 데는 0.65~~1.4초이고, 나머지는 선택 창의 파일을 앱 안으로 옮기는 단계다(플러그인 `readUriBytes`가 파일 전체를 다리로 넘김). 그동안 빈 화면이고 진행 표시도 없다. → 1.6과 3절.

### 1.4 암호 부품 (시제품 5) — 된다

- 추천은 앱 Rust 뒷단에서 `msoffice-crypto` 0.1.0(`legacy-binary`)에 CFB FAT 보정(약 60줄)을 함께 쓰는 것이다. 시험 42건(정상, 틀린 암호, 지원하지 않는 방식)을 모두 통과했다.
  - PC가 잠근 Agile·Standard 파일을 풀고, 이 부품이 잠근 파일을 PC 방식이 푼다. 바이트가 원본과 같다.
  - 잠금 매개변수가 PC와 같다(Agile, AES-256, SHA-512, spinCount 100000).
  - `.xls`는 RC4 CryptoAPI·RC4-97·XOR을 푼다. RC4-97은 Office가 만든 표본이 없어, 스펙대로 직접 만든 파일로만 확인했다.
- 틀린 암호, 지원하지 않는 방식, 변조를 따로 알린다. PC 방식은 변조를 잡지 못한다.
- 4.6 MB 파일 풀기가 30~~46 ms다(웹뷰 후보는 2.7~~3.3 s). 평문은 앱 임시 폴더 파일로만 흘려 쓰고 웹뷰로 가지 않는다. 크기는 ABI마다 약 +474 KB다.
- **보정이 꼭 있어야 한다**: PC(officecrypto-tool, SheetJS cfb)가 쓴 파일을 Rust `cfb` 0.15가 "Malformed FAT"로 거부한다.
- 걱정: 아주 새 crate라 `=0.1.0`으로 고정하고 이 시험 묶음을 앱 시험으로 옮긴다. 흘려 쓰기용 파일판 FAT 보정은 아직 없다.

### 1.5 휴대폰 PDF (시제품 6) — 된다

- PC 인쇄 HTML을 PC 함수로 그대로 만든다(`planPrintPages`·`layoutSheetPrint`·`assemblePrintHtml`). 웹뷰가 그 HTML을 스크립트 없는 숨은 iframe에 배치하면, 배치된 상자를 pdf-lib로 벡터 PDF에 옮긴다. 네이티브 코드는 필요 없다.
- 견본 셋의 모든 쪽에서 글자가 PC 결과와 같았다(404쪽 장부 전부 포함). 에뮬레이터 안에서 만든 PDF도 같았고, 글자는 고르고 찾을 수 있다. 파일은 PC보다 작다.
- 8쪽씩 묶어 그리므로 PC의 5만 칸 한도 없이 8,004쪽(90만 칸)도 나왔다(미리보기 193 s, JS 힙 최대 455 MB). Android는 쪽당 약 170 ms다(2,000행 536쪽 160 s).
- 빈틈:
  - 차트·그림이 빠진다(격자가 아직 설치하지 않음).
  - 한글 글꼴은 KS X 1001 2,350자뿐이라 한자·드문 음절은 빈 상자로 나온다. 굵은 한글은 합성이다.
  - Calibri·Arial 밖의 서양 글꼴은 Calibri 대체로 그린다.
  - PDF 전에 전체 로드가 필요하다(PC와 같음).
  - 만든 뒤 웹뷰에 약 250 MB가 남는다(실기기에서 다시 잴 것).
- OS 인쇄로 간다면 T6 소유 플러그인에 Android `createPrintDocumentAdapter`, iOS `UIPrintPageRenderer`를 더해야 하고, 3~4.5일로 어림한다. 이번에는 쓰지 않는다.

### 1.6 저장 경로 (시제품 4) — 된다(약 14 MB 아래), 큰 파일은 막힘

- 한 바퀴가 된다: 시스템 선택 창에서 고른 파일 → 앱 임시 사본(연 때의 스냅숏) → 게이트웨이 패치 저장 → `assertManifestPreserved` 목록 비교 → 엔진으로 다시 열기 → 원본에 쓰기 → 세션을 결과로 바꿈. 에뮬레이터 2,000행·30,000행 견본으로 확인했고, PC 사이드카도 결과를 열었다. 바뀐 항목은 `xl/workbook.xml`·`xl/worksheets/sheet1.xml` 둘뿐이었다.
- **바뀐 것 없는 저장은 원본 바이트 그대로다**(기기에서 sha256이 같음). 빈 계획도 엔진을 거치면 `xl/workbook.xml`(fullCalcOnLoad)이 바뀐다. 그래서 바뀐 것이 없으면 엔진을 거치지 않고 스냅숏 바이트를 그대로 쓴다.
- 다시 열기나 쓰기가 실패하면 원본(sha 그대로)과 세션은 그대로 두고, 임시 결과는 지운다.
- `.xls`·`.csv`·웹이 준 HTML `.xls`는 임시 `.xlsx`로 바꿔 연다. `.xls`는 PC `convertLegacyWorkbook`을, `.csv`는 게이트웨이 CSV 가져오기를 그대로 쓰고, 저장은 임시 `.xlsx`로 간다. 원본에는 쓰지 않는다.
- PC `writeWorkbookTo`는 본문 글자까지 똑같이 옮겨 적었다. PC 파일의 함수 글을 읽어 돌린 결과와 같은지 시험이 본다.
- Node 모듈 대역(`config/tracks/sheets.ts`의 `sheetsNodeShimsPlugin`)은 `packages/xlsx-gateway/src/gateway/*.ts`와 `apps/sheets/src/main/legacy-import.ts`에만 걸린다. 묶음에 `node:` 경고가 없다.
- **큰 파일 막힘**: 23.6 MB 견본은 원본 쓰기가 실패한다. 휴대폰 파일 부품(T6 소유)의 Kotlin `writeUriBytesAtomic`이 base64 2,000만 자 넘는 인자를 거절하기 때문이고, 약 14.3 MiB 넘는 파일의 저장·다른 이름으로 저장·공유가 모두 걸린다. 같은 함수는 대상을 `"wt"`로 열어 먼저 비우므로 원자적이지 않다(한글 저장도 같은 길). → 3절.
- **저장 메모리**(편집 저장 중 최대):

  | 견본      | 가상 파일 층 | JS 힙  | 웹뷰 렌더러 PSS |
  | --------- | ------------ | ------ | --------------- |
  | 2,000행   | 2.4 MB       | 80 MB  | 304 MB          |
  | 30,000행  | 37.9 MB      | 165 MB | 621 MB          |
  | 100,000행 | 127.5 MB     | 305 MB | 1,096 MB        |

  100,000행에서 웹뷰가 약 1.1 GB까지 올라 iPhone 한도(1.5~2 GB)에 가깝다. GC 뒤에는 160 MB로 내려가 붙잡힌 것은 없다. 게이트웨이가 시트 XML을 통째로 글로 다루기 때문이며 PC와 같은 방식이다. 줄이려면 PC 뒷단도 보내지 않는 엔진 `streamPatches`를 써야 한다.

- **열기 시간**: 이번 빌드에서는 23.6 MB 복사가 1.3~~2.0초, 고르고 첫 화면까지 6.0~~7.3초였다. T2의 80~100초는 다시 나오지 않았다. 복사가 병목은 아니다.
- 남은 일(다음 태스크): 연 뒤 원본이 바뀌었는지 확인(PC `errDiskChanged`), 다시 열기에 `shortDateFormat` 넘기기, 편집 기록 전부(시제품은 값·표시 형식만), 다른 이름으로 저장·CSV 쓰기·사본·암호 문서·오류 문장 번역.

## 2. 범위 조정안 (권장, 11-26 주인 "모두 권장대로" 승인)

1판 범위(spec 2.1~2.6)는 그대로 만들고, 시제품에서 드러난 것을 아래처럼 반영한다.

1. **격자 손짓(XLS-T8)**: 우리 손짓 층을 더한다.
   - 머리글 길게 누르기 → 우리 `Sheet`의 줄 메뉴(넣기·지우기·숨기기·너비).
   - 누르기와 두 번 누르기는 이동 거리·시간으로 판정한다(빠른 밀기가 편집을 열지 않게).
   - 편집 시작 때 그 칸을 키보드 위로 스크롤한다.
   - 손잡이 근처에서는 틀 고정 경계선을 끌 수 없게 한다.
   - 수식 입력줄 단추의 누를 영역을 `--m-hit`로 키운다.
   - 칸 길게 누르기의 Univer 메뉴를 우리 `Sheet`로 바꾸는 일은 2판으로 미룬다(그때까지는 Univer 시트).
2. **편집 기록**: 시제품은 값·표시 형식만 기록했다. 1판은 PC 편집 기록을 그대로 가져다 써서 1판 기능(서식·행·열·정렬·필터·시트 바꾸기)이 모두 저장되게 한다(XLS-T8·T9).
3. **암호(XLS-T7·T10)**: `msoffice-crypto` `=0.1.0`(`legacy-binary`)과 CFB FAT 보정을 **따로 빌드하는 엔진 라이브러리 쪽**(`src/sheets/engine-lib/`)에 둔다. 앱 크레이트의 의존 기능은 섞지 않는다. T4 시험 묶음은 앱 시험으로 옮긴다.
4. **큰 파일 저장**: 약 14 MB를 넘는 파일은 T6 부품이 바뀔 때까지 저장할 수 없다. 1판은 그 실패를 알아듣게 알리고(원본은 그대로임을 함께), 부품이 들어오면 갈아탄다(3절). 이 한도를 T1 쪽 상한으로 따로 두지는 않는다.
5. **저장 메모리**: 100,000행 편집 저장의 웹뷰 약 1.1 GB는 PC와 같은 방식이라 1판에서는 받아들이고, iPhone 실기기 숫자를 본 뒤 2판에서 `streamPatches` 사용을 검토한다.
6. **PDF(XLS-T10)**: 시제품 방식(PC 인쇄 HTML → 숨은 iframe → pdf-lib 벡터)으로 간다.
   - 저장소에 있는 Caladea·Liberation Serif/Mono를 글꼴 표에 더한다.
   - 차트·그림은 격자가 설치하면 함께 그린다. 1판 격자에서 안 되면 빠진다고 알린다.
   - 한글 2,350자 밖 글자는 빈 상자로 나온다. 빠진 글자가 있으면 PDF를 만든 뒤 한 번 알린다.
7. **열기 진행 표시**: 큰 파일을 여는 동안 빈 화면 대신 진행 문구를 보인다(XLS-T7).

## 3. 다른 트랙·공용 쪽에 바라는 것 (고치지 않음, 내용만)

- **T6 휴대폰 파일 부품(`src-tauri/plugins/tauri-plugin-ieum-mobile/**`)** — 11-26 조율 세션에 전함.
  - 원본 쓰기를 원자적으로: Kotlin `writeUriBytesAtomic`이 `"wt"`로 열어 먼저 비우지 않게, 임시 파일 → 바꿔치기(또는 최소한 잘리지 않게).
  - 파일 경로 기반 복사·쓰기: `NativeFileBridge::copy_uri_to_file(uri, path)`·`write_uri_from_file(uri, path)`(Kotlin·iOS 흘려 복사)와 저장소 공개 함수 `copy_session_to_file`·`save_file_from_path`. base64 2,000만 자 한도(약 14.3 MiB)가 사라지고, 큰 파일이 다리를 두 번 건너지 않는다. 들어오면 T1은 명령마다 한 줄쯤으로 갈아탄다.
- **PC 엑셀(주인 판단, 1판에 꼭 필요하지 않음)**:
  - `apps/sheets/src/renderer/WorkbookVisuals.tsx` 2830·2848행을 엄격한 타입 설정에서도 통과하게 손질하면 모바일의 `import.meta.glob` 우회가 필요 없다.
  - `App.tsx`의 `openLazyWorkbook` 첫 상태를 `createLazyWorkbookState(file)`로 빼면, 모바일이 다시 적은 약 60줄이 없어진다.
  - PC 비공개 값 둘(`MAX_DELIMITED_IMPORT_BYTES`, sheets-main.ts:2513; `legacyCsvCharset`, sheets-main.ts:6336)을 모바일이 되풀이해 적었다.

## 5. 발견 (합칠 때 findings 후보)

- PC 엑셀의 개인정보 열 정책(`apps/sheets/src/ai/privacy-policy.ts`)은 정의만 있고 PC 어디서도 부르지 않는다. 모바일도 PC와 같게 부르지 않는다.
- PC의 `officecrypto-tool`은 Agile 암호의 dataIntegrity HMAC를 확인하지 않는다(변조 파일도 연다). `.xls`를 풀 때 메모리를 약 75배 쓰고 Workbook 밖 스트림(VBA 등)을 버린다.
- PC 인쇄: 반복 행이 본문 중간(예: 3행)에 있으면 1쪽에서 그 위 행이 반복 행 아래에 찍힌다(Excel은 제자리).
- iOS: 엔진 세션 캐시는 샌드박스 tmp에 생긴다(`ieum-tmp/` 밖). iOS에서 `TMPDIR`을 바꾸면 WebKit까지 바뀌어 바꾸지 않았다. 고치려면 엔진 변경이 필요하다.
- 엔진이 패닉한 뒤에도 메모리 안 세션은 남는다(PC는 사이드카가 다시 떠서 세션이 모두 사라진다).
