# 워드 문서를 한글 문서로 내보내기 계획

상태: **구현됨**(2026-11-10, 사람 확인 남음). 정한 것은 결정 기록 [0121](../tracking/decisions/0121-docx-to-hwp-export.md)에 옮겼다.

## 1. 무엇을 하려는가

워드 편집기에서 연 문서를 한글 문서(.hwp, .hwpx)로 저장한다. 결과는 한컴 한글에서 열리고 고칠 수 있는 한글 문서여야 한다. 쪽 그림을 붙인 문서나 PDF를 거친 문서가 아니다. 옮기지 못한 것은 저장하기 전에 알린다.

2026-11-09 의견 보내기로 "docs to hwp 기능을 추가해주세요"라는 제안이 들어왔다. 답장할 주소는 없다.

## 2. 확인한 것 (2026-11-09~10)

변환 방법 둘을 시험했다. 시험 스크립트와 결과물은 `F:\ieum-scratch\docx2hwp-b`에 있다.

**HTML을 거치는 방법.** 워드 편집기의 HTML 내보내기 결과를 한글 엔진의 `pasteHtml`로 빈 문서에 붙였다. 글자 서식, 표, 그림은 남았다. 형광펜, 위 첨자, 제목 서식, 번호 매기기(글자 "•"로 바뀜), 안쪽 목록 수준, 쪽 나눔은 잃었다. 쪽 설정, 머리말·꼬리말, 각주는 HTML에 처음부터 없다.

**문서 구조를 직접 옮기는 방법.** `docx-engine`이 읽은 블록을 따라가며 한글 엔진 API로 새 문서를 만들었다. 시험 문서 다섯 개(직접 만든 가정통신문 모양 문서, 저장소의 각주·표·구역·기본 견본 문서)를 HWP와 HWPX로 저장했다.

- rhwp로 다시 열어 보니 10개 모두 열렸다.
- 한컴 한글 2024(공식 자동화, 스크립트가 띄운 한글만 PID로 끔)로 10개 모두 열렸다. 쪽 수가 rhwp와 같았고, 한컴이 그린 PDF가 rhwp 그림과 같았다.
- 옮겨진 것: 용지 크기·여백, 머리말, 쪽 번호, 제목("개요 1·2" 스타일), 굵게·기울임·밑줄·취소선·색·형광펜·위 첨자·크기·글꼴, 정렬·들여쓰기·여백·줄 간격, 번호 매기기와 글머리표, 합친 칸이 든 표, 그림, 각주, 쪽 나눔.
- 탭은 한컴이 기본 탭 간격으로 제대로 띄운다. 한글 탭이 저장할 때 하는 탭 폭 측정(결정 0026)이 없어도 된다.

시험 중에 찾은 것:

- **엔진의 문단 나누기는 글자 위치만 받는다.** 표, 그림, 각주 같은 개체는 글자 길이가 0이다. 그래서 다 쓴 문단을 "끝"에서 나누면 개체가 새 문단으로 끌려간다. 시험 첫판에서 표·그림·각주가 모두 문서 맨 끝 문단에 몰렸다. 맨 끝에 빈 문단을 늘 하나 두고, 그 빈 문단을 0에서 나눈 뒤 그 앞 문단에 쓰면 된다.
- 엔진의 HTML 표 붙여넣기는 첫 칸의 배경을 표 전체 배경으로도 넣는다. 그래서 표 전체가 칠해져 보인다. 표 틀만 HTML로 만들고 칸 배경은 칸마다 따로 넣는다.
- 각주 글이 각주 번호 앞에 들어갔다. 번호 뒤에 넣는다.

## 3. 정한 것

1. **들어가는 곳은 워드 편집기의 "다른 이름으로 저장"과 파일 메뉴의 내보내기다.** 결정 0110대로 "다른 이름으로 저장" 목록에 내보낼 수 있는 형식을 모두 보인다. PDF 뒤에 "한글 문서(.hwp)"와 "한글 문서(.hwpx)"를 둔다. 내보내기 형식이므로 사본을 쓴다. 열린 워드 문서의 경로와 저장 상태는 그대로다.
2. **변환은 워드 편집기 뒷단이 매번 새로 띄우는 worker thread에서 한다.** 변환은 엔진 호출 수천 번이다. 뒷단은 모든 탭과 같은 프로세스라서, 거기서 돌리면 변환하는 동안 앱 전체가 멈춘다. 엔진 메모리(WebAssembly)는 한번 늘면 줄지 않으므로 8GB PC에서 쌓인다. worker를 일이 끝날 때마다 끝내면 메모리도 돌려받고, 엔진이 죽어도 첨부 읽기에 쓰는 엔진은 멀쩡하다. 파일 찾기 색인이 이미 같은 방식(`?modulePath` worker)으로 엔진을 돌린다.
3. **변환기는 새 패키지 `packages/docx2hwp`다.** 엔진 패키지(`docx-engine`, `vendor/rhwp-core`)는 고치지 않는다. 읽기만 한다. 공개하는 것은 엔진 시작, 변환 함수 하나, 오류 형식, 그리고 잃은 것 목록의 형식뿐이다.
4. **옮기지 못한 것은 저장하기 전에 묻는다.** 이 앱의 ODT 저장(워드 편집기의 형식 바꾸기, HTML·마크다운 편집기의 ODT 내보내기)과 같은 방식이다. 잃은 것이 있으면 "빠지는 것"과 "바뀌는 것"을 나눠 보이고 [저장] [취소]를 묻는다. 없으면 바로 쓴다. 쓴 뒤에는 다른 내보내기처럼 파일을 연다.
5. **.hwp는 엔진이 스스로 다시 읽어 쪽 수가 같을 때만 쓴다.** 한글 편집기의 .hwp 저장 규칙과 같다. 다르면 .hwpx로 저장해 보라고 알린다. 어느 형식이든 다 쓴 결과를 한 번 다시 열어 본다.
6. **첫판은 한 구역이다.** 워드의 구역 나눔은 "바뀌는 것"으로 알린다. 다단, 구역마다 다른 용지는 다음 판에서 다룬다.
7. **터미널 명령어(`ieumoffice convert`)도 같은 패키지로 바꾼다(2026-11-10).** `convert <파일.docx> --to hwp|hwpx`가 앱 없이 명령 프로세스 안에서 돈다. 앱과 달리 묻지 않고 쓰며, 잃은 것은 `warnings[]`(`hwp_dropped`·`hwp_changed`)와 `detail.hwp_report`로 알린다. `.hwp`를 다시 읽지 못하면 `detail.reason: "hwp-readback"`으로 `--to hwpx`를 안내하고, 엔진이 WebAssembly 메모리를 만들지 못하면 `docs/contracts.md`의 규칙대로 `resource_limit`이다.

## 4. 데이터 흐름

```
워드 탭 렌더러 ─ buildDocBytes() ─ docx 바이트 ─▶ docs main 'docs:export-hwp'
                                                   │ 경로 허락 확인(canPdfWrite) 또는 저장 창
                                                   │ materializeLazyDocx (늦게 받는 그림을 채움)
                                                   ▼
                                          worker thread (일 하나, 끝나면 terminate)
                                          HwpEngine.start(wasm) → docxToHwp(docx, format)
                                                   │ { bytes, losses }
                                                   ▼
                                          losses가 있으면 확인 창 [저장] [취소]
                                          atomicWriteFile → openGeneratedFile
```

## 5. 패키지의 모양

**공개면.** 이것만 밖으로 낸다.

```ts
const engine = await HwpEngine.start(wasmBytes)
const { bytes, losses } = await docxToHwp(docxBytes, 'hwpx', engine)
// losses: [{ feature: 'comment', kind: 'dropped', count: 3 }, ...] (정해진 순서, 0은 뺌)
// 실패: Docx2HwpError { code: 'not-docx' | 'hwp-readback' | 'failed' }
```

호출하는 쪽은 `HwpDocument`, 단위, 문단 번호, `free()`를 보지 않는다.

**핵심 자료 구조.**

- **잃은 것 목록(`losses.ts`).** 기능 하나에 "빠짐(dropped)" 또는 "바뀜(changed)"을 적은 표 하나(`LOSS_FEATURES`)다. 보고 형식(`Loss`)은 이 표에서 만들어지므로 종류를 틀리게 적을 수 없다. 화면 이름 표(`Record<LossFeature, 문구 키>`)도 이 표를 따라야 형 검사를 지난다. ODT의 보고 ID(`REPORT_FEATURES`)는 밖과 약속한 것이라 섞지 않는다.
- **단위(`units.ts`).** 곱하는 수는 모두 여기 있다. twips→HWPUNIT ×5, twips→문단 단위 ×10(1pt=200), 반 포인트→글자 크기 ×50, px→HWPUNIT ×75, 워드 "auto" 줄 간격 240→한글 160%.
- **작은 한글 문서 모델(`model.ts`).** 문단(문단 모양, 스타일, 글 조각·그림·각주·쪽 나눔이 든 줄), 표(칸 합침, 폭, 테두리, 배경, 칸마다 문단 목록), 머리말·꼬리말, 쪽 설정. 본문, 표 칸, 머리말, 각주가 모두 같은 문단 모양을 쓰므로 쓰는 코드가 하나다. 워드 블록을 이 모델로 바꾸는 쪽은 엔진 없이 시험한다.
- **문단 커서(`cursor.ts`).** 2절의 "맨 끝 빈 문단" 규칙을 이 한 곳만 안다. 나눌 자리는 매번 문단 수에서 다시 셈하고, 다 쓰면 남은 빈 문단을 지운다. 본문·칸·머리말·각주의 엔진 호출 차이는 자리(`Place`) 하나가 숨긴다.
- **엔진(`engine.ts`).** `@rhwp/core`를 값으로 가져오는 파일은 여기 하나다. 문서는 `withNewDocument`·`withOpenedDocument`로만 만들고 `finally`에서 `free()`한다. 시험이 다른 파일의 엔진 가져오기를 막는다.

## 7. 시험

- **패키지, 실제 엔진.** 시험 문서를 HWP와 HWPX로 바꾸고 rhwp로 다시 열어 요약한다. 문단 글, 개체 위치, 스타일 이름, 글자·문단 모양, 쪽 설정, 표의 칸 합침과 칸 글, 머리말, 각주 글이 맞는지, `losses`가 정확히 무엇인지 본다. 2절의 "개체가 끝 문단으로 끌려가는" 문제는 이 시험이 지킨다.
- **패키지, 엔진 없이.** 워드 블록에서 한글 모델로 바꾸는 순수 함수를 시험한다.
- **엔진 경계.** `free()` 횟수가 만든 횟수와 같은지(성공, 실패 모두), `@rhwp/core`를 가져오는 파일이 하나뿐인지 본다.
- **워드 편집기.** "다른 이름으로 저장" 형식 목록, 경로 허락, worker가 모든 경우에 끝나는지 시험한다.
- **빌드한 앱.** 워드 탭에서 "다른 이름으로 저장" › 한글 문서로 저장해, 파일이 생기고 새 한글 탭에 열리는지 본다(Playwright, 임시 데이터 폴더).
- **한컴 한글.** 시험 문서의 결과를 한컴 한글 2024로 열어 쪽 수와 글자 수를 보고 PDF로 그려 비교한다(사람이 돌리는 스크립트).

## 8. 단계

1. 패키지: 모델, 단위, 잃은 것 표, 커서, 엔진, 변환. 실제 엔진 시험.
2. 워드 편집기: 저장 형식 목록, 내보내기 메뉴, `docs:export-hwp`, worker, 확인 창, 문구(21개 언어).
3. 도움말 "파일 작업"에 한 줄(21개 언어), 결정 기록, 프로젝트 구조(`CLAUDE.md`, `AGENTS.md`).
4. 빌드한 앱 확인, 한컴 한글 확인.

## 10. 열린 질문

- 엔진의 일괄 모드(`beginBatch`/`endBatch`)를 쓰면 글을 넣을 때마다 다시 쪽을 나누는 비용을 줄인다. 결과가 같은지, 100쪽 문서가 얼마나 걸리는지 구현하며 잰다.
- 파일 메뉴 내보내기 창에서 .hwp와 .hwpx 중 무엇을 먼저 제안할지. 설정의 "새 한글 문서 저장 형식"(결정 0089)을 뒷단에서 읽을 수 있으면 그것을 따르고, 아니면 .hwp를 먼저 둔다.
